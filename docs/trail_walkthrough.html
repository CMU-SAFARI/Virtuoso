Temporal TLB prefetcher · implementation notes

Embedding Deltas in Page-Table Entries (or On the Side)

TRAIL augments each PTE with the deltas of the translations that most often follow it. Reading a translation during a page-table walk therefore also yields the next prediction, and the walker can run ahead down the successor chain. These notes walk the implementation — the class is TemporalPTEPrefetcher; "TRAIL" is the paper name.

The mechanism · miss → learn → predict → install → hit

The implementation, stage by stage.

1

The payload: successors packed into spare bits

A region's payload is a set of k slots, each a signed delta-VPN (in region units) plus a small confidence counter. The codec lays out slot i at bits base_bit + i·(offset_bits+conf_bits), offset field first. The production layout is 4 slots of an 18-bit delta and a 2-bit counter — 80 bits, sized to the spare bits across one page-table cache line.

Deltas are stored two's-complement and decoded with an explicit sign-extension so an 18-bit field reaches ±128K regions (±4 GB at 32 KB regions):

The payload itself is a PayloadWord (256 bits) that travels with a translation and is read/written through the page table via readPayloadBits / writePayloadBits (and the 2 MB variants).

2

Learning: the table writes successors into the predecessor

On a transition src → curr (the previous region is tracked globally, or per-PC in pc_cond_learn mode), TRAIL computes the signed delta and updates the source region's payload. If no slot matches, it evicts the lowest-confidence slot in range and inserts:

The chosen slot is seeded at m_conf_init, the whole slot array is re-encoded, and the payload is written back into the source region's PTE — so next time that predecessor is walked, the successor is already present:

A matching slot instead has its confidence bumped by a pluggable ConfidencePolicy (and non-matching slots may be decayed), so a stable successor saturates its counter while stale ones age out.

3

Issue: decode the payload, gate, and chain

performPrefetch probes the page size, reads the demand region's payload, and decodes it into (delta, conf) slots. A BFS work queue drives run-ahead: depth 0 is the demand region; each accepted prediction enqueues the predicted region's payload at depth+1, up to max_prefetch_depth.

Acceptance is gated differently by depth. Depth 0 uses a plain integer confidence threshold; deeper hops use a multiplicative path score, so a long chain of weak edges is pruned:

An accepted prediction targets region + Δ and enqueues that region's own payload for the next depth — this is the run-ahead down the successor chain:

Each prediction is realized by a real page-table walk — but a transparent one: it saves the caller's clock, performs the walk to get latency, PPN, and the next payload, then restores the clock so the demand path is never charged:

Each predicted region fans out to 2^region_shift pages; one full walk is modeled per PTE cache line (the "cache-line leader") and siblings reuse its timing. The returned query_entry carries the completion timestamp.

4

Install: the prefetch queue into the L2 TLB

The TLB dedups each returned batch at region granularity (all PTEs of one prediction share a region) and pushes entries into a timestamp-ordered queue, refcounting regions and stopping at the PQ size cap:

On every later access the queue is drained: any entry whose timestamp has passed is allocated into the L2 TLB (tagged as a prefetch), and the prefetcher is notified so it can move the region from its in-flight to its installed set for timeliness accounting:

A later demand for a materialized region hits the installed entry — a pq_hit — and skips the walk; the prefetcher classifies it as demand_hit_installed and records the walk latency saved.

5

Two homes for the payload

The successors can ride in the spare bits of the PTE (v4-trail), or live in a separate OS-managed side-car (v4-trail-sidecar) — a 1 GB DRAM table with its own page-walk cache, fetched in parallel. The side-car access is modeled through the real caches (flat) or as a multi-level radix walk:

Because the side-car is fetched alongside the walk, it never changes translation latency — it only delays when a prediction can materialize, by pushing out the queue timestamps:

v4-trail

In-PTE payload

Rides in spare page-table bits, read inline during the walk. No extra structure; bounded by the ~80-bit spare-bit budget.

v4-trail-sidecar

OS radix side-car

Payload in a separate table with its own walk cache, fetched in parallel. Frees the PTE and widens the budget, at the cost of a parallel lookup.

Configuration & wiring

The knobs, and how they're read.

Defaults live in config/mmu_configs/mmu_temporal_pte.cfg; the factory turns them into an object when prefetcher_list names "temporal_pte" (tlb_prefetcher_factory.h). Per-experiment "best" points override the defaults in experiments/clist_prefetcher_v3.yaml — that YAML is the only place the in-PTE and side-car variants diverge; the two .cfg wrappers are otherwise identical.

region_shift3 – 5log₂ pages/region: 32 KB → 128 KB (also the fan-out)
modepc_cond_learntrack the predecessor globally or per program counter
max_prefetch_depth1 – 3how far to run ahead on the chain
chain_edge_decay0.85per-hop factor in the path score
chain_score_threshold0.05path-score cutoff that prunes weak chains
pq1/size1024prefetch-queue capacity
payload_in_side_tablefalse / truein-PTE vs the OS radix side-car
Note. region_shift does double duty: it sets both the prediction granularity and the fan-out — one prediction installs 2^region_shift TLB entries, but is charged only one modeled walk per PTE cache line.
